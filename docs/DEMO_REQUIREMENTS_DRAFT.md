# Local Agent Web Search Demo — 需求草案 v0.1

状态：**DRAFT / 未经用户最终确认**  
建档日期：2026-10-13  
代码状态：**尚未实施**；任何预计效果都不得标记为已测试、已通过。

## 1. 目标

验证“搜索 → 获取网页 → 提取有效正文 → 返回证据 → Agent 按需使用工具并回答”这一完整流程，在普通本地环境、不使用商业搜索 API、不开启 Chromium/Chrome 的情况下实际能跑成什么样。

重点在**可观察的真实行为**，而非界面美观、生产安全性或最终技术栈裁剪。

## 2. 本轮已经形成的共识

- 本地运行，面向未来**客户端内集成**；不以远端独立服务器为前提。
- 使用自建 SearXNG 提供搜索结果，采用 HTTP JSON 接口。
- 以 HTTPX 获取网页；Trafilatura、readability-lxml、Selectolax 参与网页解析与兜底验证。
- 允许工具功能重叠：**本轮不删减库、不提前确定赢家**；测试过程中保留可比对数据。
- 不使用 Chrome/Chromium/Playwright 浏览器渲染作为正常路径。
- 两种模式并存：**不用 AI 的关键词搜索**，以及 **AI Agent 工具调用**。
- AI 层采用 Python `openai` SDK；可按配置调用兼容服务。无需付费**搜索** API；模型端可以使用已有服务或本地兼容服务，其可用性、定价、工具支持须分别验证。
- PDF、扫描件、复杂 JS 动态页面、登录/反爬处理：**列入后续，不纳入本轮必做**。
- 本轮不以安全加固、UI 美化、生产部署为主目标。

## 3. 建议的 Demo 功能（待确认）

### 3.1 独立关键词搜索（必须）

输入：`query`、可选 `limit`、可选语言/时间限定。  
过程：请求本机 SearXNG `/search?format=json`，解析结果，必要时做 URL 去重。  
展示：标题、URL、搜索摘要、来源引擎（可获得时）、搜索响应耗时、错误。  
用户可选择某个搜索结果进行页面解析，也允许直接输入 URL。

**不需要模型，不自动生成答案。**

### 3.2 单 URL 网页读取与多工具对比（必须）

输入：一个 http(s) URL。  
过程：

1. HTTPX 下载 HTML，记录实际 URL、状态码、Content-Type、下载字节数、下载耗时。
2. 将同一份 HTML 输入多种正文提取方法，**确保公平对比**。
3. Trafilatura：主文本/Markdown 与元数据抽取。
4. readability-lxml：正文区域与主要文字提取。
5. Selectolax：DOM 清理、目标节点、结构化字段和回退文本提取。
6. 自动回退策略暂不锁定阈值；Demo 至少支持逐工具执行及展示，并输出一份当前采用的综合结果。
7. 记录每个解析器成功/失败、字数、耗时、抽取结果及采用原因。

**重要：** HTML 提取成功不等于内容质量合格；需要保留原始结果用于人工判断。HTTPX 是下载层，不是与后三者并列的正文提取器。

### 3.3 AI Agent 工具调用（必须）

接口：使用官方 Python `openai` SDK，配置 `base_url`、`api_key`、`model`。  
工具最少两个：

- `search_web(query, limit?)`：返回搜索结果及来源，供模型选择。
- `read_webpage(url)`：返回正文与标题、原始 URL、解析状态等，供模型取证。

行为：

1. 自然语言问题输入模型；由模型根据工具声明决定是否调用。
2. 本地程序执行函数，**将真实工具结果回传给模型**，继续迭代直到得到答案或达到调用上限。
3. 测试模型能否在一次问题中完成「搜索 → 读取 → 基于正文回答」。
4. 保留工具调用序列、参数、结果、错误和耗时；记录回答引用的网页 URL。
5. 验证“问题本身不需要网络”时，模型是否选择不调用搜索。
6. 如果目标模型/代理的 OpenAI 兼容接口不支持工具调用，明确报告“不兼容”，不能伪装成已成功；可用另一配置重复测试。

**接口决策待确认**：为兼容不同模型服务，可以先选 Chat Completions `tools` + 本地执行循环；Responses API 可作为之后的兼容性试验，不在本轮同时实现两套。

**注意**：本项目验证的是我们自己注册的工具，**不使用模型服务商内建 web_search 功能**来代替 SearXNG，否则无法验证本地搜索链路。

### 3.4 最小交互与观测（建议必须）

优先 CLI（或极简本地页面，不追求视觉质量）。至少可以：
- 选择 **keyword/search**、**read/url**、**agent/ask**。
- 查看搜索结果和网页提取正文。
- 显示各步骤耗时、失败原因及解析器的单独结果。
- 保存一次实验的 JSON 输出，便于横向对比。

## 4. 建议的测试用例

| 类别 | 验证点 | 本轮目标 |
| --- | --- | --- |
| 简单静态文章 | 标题、正文与来源可读 | 必测 |
| 新闻与杂项导航很多的页面 | 去噪与提取质量 | 必测 |
| 技术文档 | 标题/正文/代码段表现 | 必测 |
| 带 JSON-LD/框架内嵌数据的页面 | Selectolax 等是否能补救 | 可选 |
| 纯 JS 动态页面 | 正确报“无可用正文”而非编造 | 必测负例 |
| 403/404/超时 | 错误报告和兜底边界 | 必测负例 |
| 独立关键词查询 | 搜索结果是否可用 | 必测 |
| Agent 需要实时信息的提问 | 是否调用搜索及读取 | 必测 |
| Agent 普通知识提问 | 是否可以不调用工具 | 必测 |
| 证据不足的问题 | 是否承认检索失败/不足 | 必测 |

指标：搜索耗时、HTML 下载耗时、各提取器耗时、成功率、正文质量的人工判断、Agent 真实工具调用次数、回答是否引用实际访问过的页面。

## 5. 待确认的决策（不应擅自视为定案）

1. 入口：CLI 先行，还是需要一个极简 Web 页面？
2. 本地环境：优先 Windows、Linux，还是两者都做首轮验证？
3. SearXNG：本机 Docker 自建，还是使用已运行的本地实例？
4. 模型兼容：先仅测 Chat Completions `tools`，还是必须同时验证 Responses API？
5. 结果格式：仅在终端输出 JSON/文本，还是额外落盘 Markdown/JSON？
6. 网页解析：自动使用结果选择策略的具体质量判据和顺序，本轮调研后再定。

## 6. 推荐分阶段验收（草案）

- **M0**：本地启动 SearXNG，JSON 接口能返回搜索结果。
- **M1**：关键词搜索、URL 下载、三个提取器独立运行，并有可比对记录。
- **M2**：多提取器输出汇总与回退策略可观察。
- **M3**：OpenAI SDK 可连接指定模型，并成功完成至少一次真实函数调用。
- **M4**：Agent 完成搜索→网页读取→回答闭环；报告成功与失败场景。
- **M5**：汇总实验记录，不预设裁剪结论。

以上只是计划，不代表测试已发生。
